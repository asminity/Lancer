# AUTONEX Checkpoint Engine: AI Context Snapshot Specification (Phase 4)

## 1. Overview & Architectural Objective

A codebase snapshot alone is insufficient to resume multi-agent autonomous engineering. Without the exact cognitive context under which a state was reached, resuming agents suffer from **split-brain syndrome** (violating Global Development Rule 5):
- The restored code reflects an older state (e.g. Milestone 2 in-flight).
- The agent reasoning reflects a newer or completed state (e.g. Milestone 5 completed).
- Agents attempt to execute against code that does not exist or contradict architectural decisions previously made.

The **AUTONEX AI Context Snapshot Engine** captures, encrypts, and persists the complete, authentic cognitive state of the agent floor corresponding bit-for-bit to each code checkpoint.

When an older checkpoint (such as `CP-003`) is restored, the AI floor's tasks, active instructions, notes, and memory are reverted to `CP-003` without retaining residue from `CP-005`.

---

## 2. Information Captured

Every context snapshot captures 15 distinct dimensions of the multi-agent session:

| # | Dimension | Description |
|---|---|---|
| **1** | **Project Identity** | `projectId`, `projectName`, `goal`, target output directory. |
| **2** | **Current Objective** | High-level goal and active milestone objective. |
| **3** | **Current Task** | Active task ID (`currentTaskId`) and description currently being executed. |
| **4** | **Completed Tasks** | List of all completed DAG nodes with results, previews, and dependencies. |
| **5** | **Pending Tasks** | List of pending DAG nodes scheduled for subsequent execution. |
| **6** | **User Requirements** | Extracted explicit constraints, goal definitions, and rules. |
| **7** | **Architecture Decisions** | Pinned architectural patterns, frameworks, and design choices. |
| **8** | **Agent Decisions** | Pinned agent consensus, gate approvals, and model choices. |
| **9** | **Files Created** | Explicit list of files generated by the agents up to this checkpoint. |
| **10** | **Files Modified** | List of files modified with line ranges and editing agent metadata. |
| **11** | **Files Deleted** | List of files deleted or superseded during execution. |
| **12** | **Execution Status** | `In Progress` \| `Interrupted` \| `Completed`, simClock, elapsed time. |
| **13** | **Conversation Summary** | Executive summary of progress, completed milestones, and blockers. |
| **14** | **Next Recommended Action** | The immediate next step for the resuming agent. |
| **15** | **Continuation Instructions** | Clear, actionable prompt for the incoming worker/lead agent. |

## 3. Secret & Credential Sanitization Policy

Before serializing the context snapshot, all sensitive credentials are scrubbed by `sanitizeContextText()`:
- **Private Keys:** Any `0x[a-fA-F0-9]{64}` sequence is replaced with `[REDACTED_PRIVATE_KEY]`.
- **API Keys:** `0g-[a-zA-Z0-9]{16,}` and `sk-[a-zA-Z0-9]{20,}` are replaced with `[REDACTED_0G_KEY]` and `[REDACTED_API_KEY]`.
- **Bearer Tokens:** `Bearer <token>` patterns are replaced with `Bearer [REDACTED_TOKEN]`.
- **Passwords:** Any `password/passwd/pwd was/is/:/=` prose or config is scrubbed to `password=[REDACTED_PASSWORD]`.
- **Env Variables:** Assignments to `SECRET_KEY`, `TOKEN`, `API_KEY` are scrubbed to `$1=[REDACTED]`.

## 4. Versioned Schema (`2.0.0`)

```typescript
export interface CheckpointContextV2 {
  checkpointId: string;
  projectId: string;
  schemaVersion: '2.0.0';
  createdAt: string;
  agentTaskId: string | null;
  parentCheckpointId: string | null;
  payload: ContextPayload;
  contextChecksum: string; // SHA-256 of canonical payload JSON
}
```

---

## 5. Encryption & Decentralized Storage (Ethereum Swarm)

1. **Serialization:** Context is serialized into canonical JSON and encoded to UTF-8 bytes.
2. **Integrity Checksum:** Cryptographic SHA-256 hash is computed over the payload bytes (`contextChecksum`).
3. **Authenticated Encryption:**
   - Algorithm: `AES-256-GCM`.
   - Key: 256-bit symmetric key (`crypto.randomBytes(32)` or derived key).
   - IV: Unique 96-bit (12-byte) initialization vector per snapshot.
   - Authentication Tag: 128-bit (16-byte) GCM authentication tag.
4. **Decentralized Storage:**
   - The encrypted ciphertext bytes are uploaded to **Ethereum Swarm** using the official Bee JS SDK (`SwarmStorageProvider.uploadBinary`).
   - A real 64-character Swarm reference (BZZ hash) is obtained.
   - Zero mock storage, zero fake references, zero local-only masquerading (Global Rule 2 & 6).

## 6. Restoration & Agent Rehydration Pipeline

When a checkpoint is restored:

```
[Swarm Reference]
       │
       ▼
1. Download from Swarm via Bee SDK (`downloadBinary`)
       │
       ▼
2. Decrypt AES-256-GCM with Checkpoint Key (`decryptPayload`)
       │
       ▼
3. Validate Schema Version (`schemaVersion === '2.0.0'`)
       │
       ▼
4. Verify SHA-256 Checksum (`contextChecksum === actualSha256`)
       │
       ▼
5. Rehydrate `useStore` Application State (`applyRestoredContextToStore`)
       ├── Reconstruct Tasks DAG (Completed, Running, Pending)
       ├── Reconstruct Agent Roster & Assign Active Tasks
       ├── Reconstruct Blackboard Notes & Architectural Directives
       └── Set Active Agent Continuation Instructions
```

### Failure Handling
If context download, decryption, or checksum verification fails:
- **No Hallucination:** The system does **not** invent or generate synthetic context.
- **No Stale Substitution:** The system does **not** substitute context from a newer checkpoint.
- **Codebase Preserved:** The restored workspace files remain intact.
- **Controlled Alert:** The UI notifies the user that context restoration failed and offers an explicit recovery option.

## 7. Dual Checkpoint Isolation Proof (CP-003 vs CP-005)

The test suite in [`frontend/src/tests/checkpoint-context.test.ts`](file:///home/pritul-singh/AUTONEX/frontend/src/tests/checkpoint-context.test.ts) proves that:

1. **CP-003 Setup:**
   - 1 Task Done (`T1`), 1 Task Running (`T2`), 1 Task Pending (`T3`).
   - Active Agent: Rohan (`W_backend_0`) assigned to `T2`.
   - Continuation Instruction: `"CP-003 Instruction: Continue writing order placement REST API in backend/routes.py."`
2. **CP-005 Setup:**
   - 3 Tasks Done (`T1`, `T2`, `T3`), 1 Task Running (`T4`), 1 Task Pending (`T5`).
   - Active Agent: Kabir (`W_qa_0`) assigned to `T4`.
   - Continuation Instruction: `"CP-005 Instruction: Verify stress test throughput benchmarks and prepare L2 deploy script."`
3. **Restoration Verification:**
   - Restoring CP-003 immediately removes `T4` and `T5` from the store.
   - Restores `T2` to `running` and `T3` to `pending`.
   - Replaces continuation instruction with CP-003 instructions.
   - Restores Rohan as the active working agent on `T2`.
   - Restoring CP-005 reverts back to the advanced state with `T4` and `T5`.
